\section{Overview of Proposed Methodology}
\label{sec:overview}
This research implements and evaluates an automated testing pipeline that uses Large Vision-Language Models (VLMs) for dynamic web UI anomaly detection. The methodology divides into four stages. First, automated fault injection renders synthetic control and experimental UI interaction sequences using Playwright. Second, a quality gate filters the raw video assets by pixel-level difference analysis, so that the ground truth is unambiguous. Third, a dual-path detection pipeline routes visual signals and DOM mutation events to specialised reasoning paths. Fourth, empirical benchmarking evaluates a multimodal model with structured JSON responses under zero-shot settings, across a factorial ablation of the pipeline's own design choices.

\section{Data Preparation and Generation}
\label{sec:data_prep}
The quality and quantity of testing data matter for evaluating multimodal models. To keep results relevant and valid while avoiding manual annotation overhead, fault injection was automated end to end, producing structured, reproducible datasets.

\subsection{Dataset Generation}
\label{sec:data_prep-generation}
Testing data was generated by scripted Playwright sessions against a single deployed instance of TodoMVC's React reference implementation (\url{https://todomvc.com/examples/react/dist/}), run headless in Chromium at a fixed \num{1280}$\times$\num{720} viewport. Six categories of dynamic visual defect were injected programmatically into otherwise-normal interaction sequences: \texttt{flyaway\_offset}, \texttt{vanish\_invisible}, \texttt{flicker\_seizure}, \texttt{displaynone\_collapse}, \texttt{skew\_distortion}, and \texttt{blur\_unreadable}. Injection is deterministic and driven entirely by a single RNG seed (\texttt{rngSeed}, identical across a generation run) combined per scenario with an FNV-1a hash of the scenario id, so the dataset can be regenerated from the seed rather than existing only as a one-off artefact; the generator never calls \texttt{Math.random()}. Local host instances and isolated DOM environments were enforced throughout, to keep out environmental noise and external anti-bot mechanisms such as CAPTCHA challenges.

\paragraph{A dataset-integrity incident and its fix.} An early version of the dataset (\texttt{dataset\_v1}) passed a screenshot-based pixel-difference gate on all 40 cases, but frame-level inspection later showed that several \emph{videos} never actually displayed the labelled defect. Playwright's recorder finalises the clip asynchronously on browser-context close, so a static broken state, such as the application vanishing or moving off-screen, could lose that race and never reach the recorded video, even when the corresponding screenshot was correct. This was caught before any model evaluation ran on the affected data. Three changes followed. First, a fixed 7-second post-injection hold, identical for normal and defective clips so that duration itself cannot leak the label, paired with a low-frequency ``heartbeat'' marker outside the application's clip region that forces the recorder to keep emitting frames through an otherwise static broken state. Second, a dedicated \emph{video-level} quality gate (Section~\ref{sec:data_prep-qg}) that decodes the final frame of every clip and checks it resembles the defective reference image rather than the normal one, instead of trusting the screenshot. Third, removal of a label leak in the interaction script itself: it had been typing the scenario id, including the bug's name, into the on-screen todo input after injection; post-injection typing now uses neutral, defect-agnostic phrases. All three fixes were verified against a regenerated dataset before any further use.

\paragraph{Final dataset (\texttt{dataset\_v3}).} The dataset used for the formal trial reported in Chapter~\ref{chap:results_and_discussion} contains \textbf{120 clips}: 60 normal (control) and 60 anomalous, with the anomalous half balanced exactly 10 clips per bug type across the six categories above. Table~\ref{tab:dataset-composition} summarises its composition. Every clip is accompanied by a \texttt{.webm} recording, a \texttt{domtrace.json} MutationObserver log (Section~\ref{sec:data_prep-dom}), and \texttt{normal}/\texttt{buggy}/\texttt{diff} reference screenshots. An earlier, smaller dataset (\texttt{dataset\_v2}, 40 clips, 8 normal / 8 anomalous per the pilot subset used in Section~\ref{sec:exp_design}) was used only for the initial pilot trial and is not part of the formal evidence base.

\subsection{Feature Engineering and Data Pre-processing}
\label{sec:data_prep-qg}
Following data generation, the raw video assets went through feature engineering and pre-processing to improve model evaluation consistency and efficiency: extracting temporal keyframes and tracking DOM mutation records to give the model more to reason from. Two independent automated quality gates had to pass before any clip was eligible for benchmarking. The screenshot-level gate (\texttt{pixelmatch}) verifies zero pixel difference between the recorded normal-state screenshot and the reference normal image for control cases, and a per-bug-type minimum YIQ difference ratio (threshold range \numrange{0.05}{0.15}) between the buggy and normal reference screenshots for anomalous cases. The video-level gate, added after the incident described above, decodes the final frame of the recorded \texttt{.webm} and checks that it sits closer to the defective reference than to the normal reference for anomalous clips, and that no defect is visible for controls.

On the final dataset, the video-level gate passed \textbf{120/120} clips with zero failures: all 60 buggy clips returned a last-frame difference of \numrange{0.1091}{0.6927} against the normal reference (and near-zero against the buggy reference), confirming the injected defect is provably present \emph{on the recorded video}, not merely in the paired screenshots the earlier, weaker gate relied on. \subsection{DOM Mutation Recording}
\label{sec:data_prep-dom}
Alongside each recording, a \texttt{MutationObserver} attached to the page body logs every DOM mutation (type, target tag, timestamp) for the duration of the clip, producing \texttt{domtrace.json}. This is the structural half of the dual-path signal used in Section~\ref{sec:system_architecture}. All six injected defects are implemented as CSS rules inserted into the document \texttt{<head>}, which the body-level observer does not see; genuine user interactions, such as adding, completing, or deleting a todo item, always mutate the DOM body. Visual change with no corresponding DOM mutation is therefore unusual, while visual change accompanied by a DOM mutation is the normal case. This asymmetry is what the dual-path architecture and the fused frame selector (Section~\ref{sec:system_architecture-fusion}) exploit, and it is also, mechanically, why the DOM trace cannot leak the injected label (Section~\ref{sec:label_leak}): the trace records only what the browser's mutation API reports, and CSS-only injections are invisible to it by construction.

\section{System Architecture and Pipeline Design}
\label{sec:system_architecture}
This section details how the dual-path filtering and comparison framework was built, and gives the mechanism by which the ground-truth label is kept out of every prompt sent to the judge model. This design property was probed at the interim demonstration, so it is explained here at the level of the actual code rather than only in prose.

\subsection{Frame Selection as an Ablation Factor}
\label{sec:system_architecture-selection}
Rather than treating ``how the model sees the clip'' as a fixed design choice, the pipeline implements three interchangeable frame-selection strategies and evaluates all of them under the same judge, so the contribution of selection can be isolated from the contribution of prompting (Section~\ref{sec:exp_design}). \textbf{Uniform sampling (A0)} takes six frames spaced evenly across the whole clip: the naive ``just show the model some frames'' baseline, with no selection logic at all. \textbf{Pixel-only keyframe selection (A1)} locates the strongest \emph{sustained} pixel transition in the clip by scoring every candidate frame index on the difference between the state a small window before it and a small window after it, deliberately not biased toward the end of the clip even though injected defects tend to persist there; the before frame, the after frame, and the clip's final frame are returned. \textbf{Pixel+DOM fused selection (A3)} runs the same transition search as A1, but each candidate's pixel score is down-weighted by the amount of DOM activity recorded near its timestamp,
\begin{equation}
\text{fused\_score}(i) = \frac{\text{pixel\_score}(i)}{1 + \lambda \cdot \text{dom\_mutations\_near}(i)},
\end{equation}
with $\lambda = 1$ and a $\pm\SI{1200}{\milli\second}$ window. Because CSS-only defects change pixels without a DOM mutation while ordinary user edits produce both, this rule is designed to prefer the CSS-only-looking transition when one exists, so the DOM trace genuinely changes \emph{which} frame is sent, not merely what is said about it.
\label{sec:system_architecture-fusion}

All three selectors operate on the decoded frame buffer and, for A3, the DOM trace; none of them receives the clip's ground-truth label, bug type, or expected verdict as an input (Section~\ref{sec:label_leak}).

\subsection{Prompting as an Ablation Factor}
Two prompt designs are evaluated, factorially crossed with the three selectors above. The \textbf{naive prompt (B0)} states only that $k$ frames are shown and asks for a JSON verdict (\texttt{anomaly}/\texttt{normal}) with a one-sentence reason; it says nothing about how the frames were chosen, so it stays a fair control regardless of which selector supplied them. The \textbf{dual-path decision prompt (B1)} additionally supplies a generic, clip-independent description of the application's expected appearance, the timestamp and structural signal (change ratio, changed-region bounding box, oscillation count, post-transition persistence) describing the selected transition, and a compact summary of DOM mutation activity near that transition. The model is told that a visual transition unaccompanied by DOM activity is suspicious, while content changes coinciding with DOM mutations are normal user actions. Both templates constrain the output to a single JSON object with an out-of-schema-free \texttt{verdict} field (and, for B1, a \texttt{defect\_type} field restricted to the six known categories or \texttt{null}), so scoring never has to parse free text.

\subsection{Preventing Label Leakage in the Judge Prompt}
\label{sec:label_leak}
A concern raised in discussion of this project is whether the ground-truth label could, deliberately or accidentally, end up in the information sent to the judge model, which would make the reported accuracy figures meaningless. This subsection gives the argument at the level of the code that actually builds each request, so the claim can be checked rather than taken on trust.

Each clip's manifest record (\texttt{data/manifest.json}) carries five label-bearing fields: \texttt{ground\_truth}, \texttt{is\_anomaly}, \texttt{bug\_type}, \texttt{bug\_label}, and a natural-language \texttt{expectation} string (for example, ``the application card should be sharply rendered'' for a blur defect). These fields exist because the \emph{scorer} needs them: \texttt{pipeline/score\_trial.py} reads \texttt{case[``ground\_truth'']} and \texttt{case[``bug\_type'']} to compare against the model's returned verdict, strictly \emph{after} a response has already been generated and cached. The function that builds the request sent to the model, \texttt{build\_condition\_payload()} in \texttt{pipeline/run\_trial.py}, and the function that decodes and analyses a clip, \texttt{analyze\_clip()}, both take the same \texttt{case} dictionary as an argument but read only two of its fields, \texttt{video\_path} and \texttt{dom\_trace\_path}, to load pixels and the DOM trace. Neither \texttt{ground\_truth}, \texttt{is\_anomaly}, \texttt{bug\_type}, \texttt{bug\_label} nor \texttt{expectation} is referenced anywhere between decoding the clip and sending the API call; a grep of the request-construction path for these five field names returns no matches outside the scorer.

Three further points reinforce this. The frame selectors are label-blind by construction: \texttt{select\_transition()} (A1) and \texttt{select\_fused()} (A3) take only the decoded frame array, frame rate, and, for A3, the DOM trace as arguments, and there is no code path by which either function could reach the manifest. This is stated directly in the module's own docstring (\texttt{pipeline/keyframes.py}): ``Nothing in this module reads the ground-truth label -- selection is driven only by pixels (A1) or pixels + DOM structure (A3).'' The B1 prompt's ``expected appearance'' text is generic rather than per-clip: \texttt{EXPECTED\_APPEARANCE} is a single hard-coded string describing the nominal look of the TodoMVC application (card layout, colours, typography) that is identical for every one of the 120 clips and every one of the six bug types, and it is not derived from, or varied with, the manifest's per-clip \texttt{expectation} field, which is reserved for scoring and never formatted into a prompt. And the structural signals passed to the model describe the transition, not the injection: the \texttt{signal} dictionary attached to a selection (change ratio, bounding box, oscillation count, DOM mutation counts) is computed purely from pixel and DOM data at the selected timestamp, with no bug-type string, confidence score, or boolean flag copied from the manifest.

Two further design choices, both closely tied to labelling, were made deliberately to avoid \emph{indirect} leakage. The post-injection hold duration is fixed at 7 seconds identically for normal and anomalous clips (Section~\ref{sec:data_prep-generation}), so clip duration cannot serve as a proxy for the label. And a pixel-only probe run during pilot development confirmed that raw frame-difference magnitude does not separate the two classes (ordinary typing produces larger pixel differences than several of the injected bugs), so a selector that simply chased ``the biggest change'' would not have been exploiting a shortcut correlated with the label. Taken together, the manifest's label fields stay isolated to the scoring step, which runs only after every response has already been generated and cached; there is no mechanism by which a change to the scorer could retroactively alter what any judge call actually saw.

\section{Model Selection and Environment Setup}
\label{sec:env_setup}

\subsection{Model Selection}
\label{sec:env_setup-model}
The project was originally scoped to compare a commercial multimodal API model against an open-weight model run locally (Qwen2.5-VL) on department GPU infrastructure, so the method's generality across judge models could be assessed alongside the ablation of its own design. In practice, this cross-model comparison was dropped before the formal trial ran. The reason is methodological rather than practical: the contribution under test in Chapter~\ref{chap:results_and_discussion} is the keyframe-selection and decision-prompting layers of the pipeline, not the underlying VLM, and holding the judge model fixed across every one of the 1{,}440 calls in the formal trial removes judge identity as a confound in the factorial ablation. Running the same ablation a second time against Qwen2.5-VL to check cross-model generality is recorded as future work (Section~\ref{chap:conclusion}) rather than attempted with reduced statistical power inside the present study.

The judge model actually used for both the pilot and the formal trial is \textbf{Gemini 3.1 Flash-Lite} (\texttt{gemini-3.1-flash-lite}), accessed through the Google Gemini API (\texttt{google-generativeai==0.8.6}). The model identifier is pinned explicitly for the formal trial: \texttt{vlm\_client.connect()} checks the pinned id against the account's live model list, and the run aborts rather than silently substituting a different model on a quota error, so no cell of the ablation could see a different judge than any other. Every one of the 1{,}440 cached responses in the formal trial reports \texttt{model: gemini-3.1-flash-lite}, confirming the pin held for the entire collection run. Generation parameters were fixed identically across all conditions: temperature \num{0.0}, top-$p$ \num{1.0}, top-$k$ \num{1}, maximum output tokens \num{512}, one candidate per call. Temperature \num{0.0} makes decoding greedy, but the API does not guarantee bit-identical output across sessions; this residual non-determinism is absorbed by repeating every (clip, condition) cell three times and scoring the per-clip majority vote (Section~\ref{sec:exp_design}).

\subsection{Server and Library Settings}
Dataset generation (Playwright rendering, fault injection, and video/DOM capture) and the automated quality gates were run locally. Judge inference for both the pilot and the formal trial went exclusively through the Gemini API over the network; no local GPU inference was performed for the results reported in this dissertation, since the open-weight comparison described above was descoped before collection. The software environment used throughout the pipeline comprises \texttt{Playwright} for automated browser rendering and interaction scripting, \texttt{pixelmatch} and a custom YIQ-difference routine for the screenshot- and video-level quality gates, \texttt{imageio-ffmpeg} and \texttt{NumPy}/\texttt{Pillow} for video decoding and frame resizing, \texttt{google-generativeai} for judge inference, and \texttt{SciPy} for the statistical tests described in Section~\ref{sec:benchmarking}. The project's supervisor-mandated statistics rule specifies \texttt{statsmodels}, but that package was absent from the locked environment at collection time; this deviation is disclosed here and again at first use in Chapter~\ref{chap:results_and_discussion}, since Cochran's Q was in that case implemented directly rather than imported.

\section{Experimental Design: Pilot and Formal Factorial Ablation}
\label{sec:exp_design}
Two experiments are reported in this dissertation, both governed by a written freeze policy: once an experiment's configuration file is marked \texttt{frozen}, no field in it (model, prompts, generation parameters, dataset, or statistical procedure) may change while results are being collected. Any change requires a new experiment identifier and a full re-run of every clip under every condition, because a partially re-run design breaks the paired statistical tests used to analyse it.

\textbf{EXP001 (pilot)} compared two end-to-end configurations: uniform sampling with the naive prompt, and pixel-only keyframe selection with the dual-path prompt, on a balanced 16-clip subset (8 normal, 8 anomalous, all six bug types represented) drawn from an earlier dataset version. Table~\ref{tab:pilot-results} reports its result. The pilot's ``ours'' condition selected frames by pixels alone, so under the factor scheme adopted for the formal trial (below) it is condition A1B1, not the fused-selection condition its original description implied.

The pilot's direction was consistent (A1B1 dominated A0B0 on every discordant clip: 3 clips favoured A1B1, none favoured A0B0), but at $n=16$ it was not statistically decisive: exact McNemar on the discordant pairs gave $p=0.25$. A pre-registered Monte-Carlo power analysis (100{,}000 simulations per cell, seed \texttt{20260727}), using the pilot's discordant-pair rate and split only as a planning basis, found that $n=16$ was underpowered and that the full 120-clip dataset would reach a simulated power of \num{0.94} at a planning discordant-pair rate of \num{0.20} and split $\psi=0.85$, comfortably above the conventional \num{0.80} threshold, while an intermediate $n=40$ exploratory sample reached only \num{0.38}. The pilot's own observed split ($\psi=1.00$) was deliberately not used for planning, since a perfect split at $n=16$ with zero discordant pairs on one side is a winner's-curse-inflated estimate rather than a safe planning figure. On this basis, the formal trial evaluates the entire 120-clip dataset rather than generating additional videos or drawing a smaller exploratory sample.

\textbf{EXP002 (formal trial)} extends the pilot's two-endpoint comparison into a $2\times$3-level factorial ablation: \textbf{Factor A} (which frames are sent) at levels A0 (uniform), A1 (pixel-only keyframes), and A3 (pixel+DOM fused keyframes); \textbf{Factor B} (which prompt is used) at levels B0 (naive) and B1 (dual-path). Of the six possible combinations, four make up the headline design: \textbf{A0B0}, \textbf{A1B1}, \textbf{A3B0}, and \textbf{A3B1}. These were chosen so that A0B0$\to$A3B0 isolates the contribution of frame selection under a fixed naive prompt, A3B0$\to$A3B1 isolates the contribution of the dual-path prompt under fixed fused selection, and A1B1 anchors the pilot's original condition for continuity. A2 (a DOM-only selector) and A1B0 (the pixel-only-selector, naive-prompt cell needed to fully de-alias the two factors) were considered and deliberately left out of this trial; both are discussed as limitations and future work in Chapter~\ref{chap:results_and_discussion}. Every one of the 120 clips is evaluated under all four conditions, each repeated 3 times. Repeats capture residual API non-determinism at temperature 0 rather than sampling diversity, and are collapsed by majority vote before the paired tests, giving $120 \times 4 \times 3 = \mathbf{1{,}440}$ total API calls. Conditions and repeats are interleaved per clip during collection, so a quota interruption loses the same clips from every arm and the paired design survives regardless of when the run stops.

Both experiments' configurations were frozen \emph{before} collection began, each pinning the model, both prompt templates by SHA-256 hash of their exact source string, the generation parameters, the dataset, and the statistical procedure to be applied. EXP002's naive prompt differs from EXP001's by a few words: a phrase claiming uniform sampling was removed, since it would be a false claim under the A3 selector, and is versioned and hashed separately as a result. This is recorded as an intentional, disclosed change between experiments rather than drift within one. A structural refactor of the pipeline code was carried out \emph{before} EXP002's first API call and verified, by byte-for-byte comparison of every artefact the refactored code could produce (prompt hashes, the manifest, the pilot's re-scored summary, decoded-frame pixel hashes, and the video quality-gate report) against pre-refactor baselines, to have made no behavioural change. No refactor was carried out once collection was underway.

\section{Evaluation Metrics and Benchmarking}
\label{sec:benchmarking}
Benchmarking is central to evaluating and comparing Vision-Language Models in software engineering. To keep this consistent, standardized metrics were chosen for binary anomaly classification and structured defect extraction.

\subsection{Point Metrics}
The evaluation metrics used in this research are accuracy, recall (true positive rate), and false positive rate (FPR). Accuracy measures the proportion of correctly identified normal and defective UI sequences over the total dataset. Recall computes the ratio of correctly identified anomalies out of all actual injected defects,
\begin{equation}
    \text{Recall} = \frac{\text{True Positives}}{\text{True Positives} + \text{False Negatives}},
\end{equation}
and the false positive rate measures how often nominal UI transitions are misclassified as bugs,
\begin{equation}
    \text{FPR} = \frac{\text{False Positives}}{\text{False Positives} + \text{True Negatives}}.
\end{equation}
All VLM outputs are constrained via JSON Schema to log a binary status (\texttt{verdict}), a defect category (\texttt{defect\_type}, B1 conditions only), and explanatory reasoning for transparent analysis. A response whose \texttt{verdict} field falls outside \{\texttt{normal}, \texttt{anomaly}\} counts as incorrect for accuracy purposes but is recorded separately as a \emph{schema-compliance} failure, since a well-formed but out-of-vocabulary answer (observed once in the formal trial; see Section~\ref{sec:results-discoveries}) is a different failure mode from a genuine misclassification, and the two must not be conflated when reporting detection rate.

\subsection{Dispersion and Statistical Testing}
Following a reporting rule set by the project supervisor after an interim progress review, every metric in this dissertation is reported as mean $\pm$ SD with an accompanying 95\% confidence interval and sample size, in the form $\text{mean} \pm \text{SD}$ [95\% CI] ($n=N$), rather than as a bare point estimate. Two independent sources of dispersion feed into this. Run-to-run SD comes from executing each condition 3 times per clip (Section~\ref{sec:exp_design}) and reporting the standard deviation across those 3 repeats for accuracy. Bootstrap SD and CI come from drawing \num{10000} resamples, with replacement, over the per-clip outcome vector for each metric, seeded at \texttt{20260728}, and reporting the resulting distribution's standard deviation and 2.5th/97.5th percentiles.

Comparisons between conditions use a fixed hierarchy of paired, non-parametric tests, since every comparison is within-clip (the same 120 clips are evaluated under every condition). An omnibus \textbf{Cochran's Q test} over the per-clip correctness matrix asks whether the four conditions differ at all before any pairwise comparison is attempted. If that omnibus test is significant, pairwise \textbf{exact McNemar tests} on the discordant pairs of each condition pair follow, with \textbf{Holm-Bonferroni correction} across the six pairwise comparisons and \textbf{Cohen's g} as the accompanying effect size. Paired, continuous efficiency metrics (total tokens, latency, cost) are compared with the \textbf{Wilcoxon signed-rank test}, again Holm-corrected across the six pairwise comparisons, with \textbf{matched-pairs rank-biserial correlation} as the effect size. No p-value is reported without an accompanying sample size and effect size, and no non-significant result is described as a positive finding. All statistics are written to a machine-readable summary alongside the analysis code that produced them, so every figure quoted in Chapter~\ref{chap:results_and_discussion} traces back to the cached raw responses rather than being recomputed by hand.

\subsection{Cost Model}
Token usage (prompt, candidate, and total tokens) is read directly from each API response's usage metadata rather than estimated, and converted to cost using the pinned model's published per-token rate card (\$0.25 per million input tokens, \$1.50 per million output tokens). A run flags whether its rate card was confirmed for the specific pinned model or assumed by default, so a cost figure is never silently computed against the wrong price.

\section{Division of Labour: Manual Design and Automated Execution}
\label{sec:division_of_labour}
A question raised during the interim demonstration concerned which parts of this project's pipeline are manual and which are automated, and, relatedly, where an AI coding assistant was used and how its output was checked. This section answers both questions directly.

\subsection{What is automated at run time}
Once launched, the pipeline needs no manual intervention: fault injection, video and DOM-trace capture, both quality gates, keyframe selection at all three levels, prompt construction, judge API calls, response caching, and scoring all run by script with no per-clip or per-condition human input. Ground-truth labels for every clip are derived automatically from the injected bug key at generation time (Section~\ref{sec:data_prep_generation_labels}), not hand-annotated, which is what lets the 120-clip dataset, and a re-run of the whole pipeline against a freshly generated dataset from the same seed, be reproduced without renewed manual labelling effort.
\label{sec:data_prep_generation_labels}

\subsection{What was decided by hand}
The choices that determine \emph{what} the automated pipeline does were made by the author and are not themselves learned or automated: the six-category bug taxonomy and its CSS/DOM injection mechanics; the decision to hold post-injection duration fixed across classes to avoid a timing leak; the two-factor (selection $\times$ prompt) ablation design and which four of six possible cells to run; the fusion rule and its parameters ($\lambda=1$, $\pm\SI{1200}{\milli\second}$ window); the choice of statistical tests and the decision to run a pre-registered power analysis before committing to the formal trial's scale; the freeze policy itself and its exceptions; the post-hoc decision, once results were in, to designate A1B1 rather than A3B1 as the pipeline's headline configuration (Section~\ref{sec:results-decisions}); and the decision not to run the additional A1B0 cell that would have de-aliased one contrast, since doing so after seeing the results would need a new, separately pre-registered experiment rather than an ad hoc addition to a frozen one.

\subsection{Use of an AI coding assistant}
An AI coding assistant (Claude Code) was used throughout the implementation phase of this project, mainly to draft and refactor the Python pipeline modules described in Section~\ref{sec:system_architecture} once their design had been specified, to build the statistical analysis scripts to the specification in Section~\ref{sec:benchmarking}, and to reconcile reported figures (for example, in progress communications to the supervisor) against the cached raw results, catching reporting errors before they were sent. In every case, the assistant worked from a specification, a bug taxonomy, a factorial design, a fusion rule, a choice of statistical test, that had already been decided by hand as listed above. It was not used to choose the experimental design, to select which findings to report, or to decide the contribution reframing described in Section~\ref{sec:results-decisions}; those were reviewed and decided by the author. Assistant-proposed changes were not accepted uncritically: a suggestion to run the additional A1B0 cell as a declared supplementary experiment once the fusion-harms-accuracy finding emerged, for instance, was considered and rejected, for the pre-registration reason given above. A complete, dated log of the prompts used, a summary of the assistant's contribution at each stage, what was independently verified before being relied upon, and which suggestions were accepted or rejected is kept as an appendix to this dissertation (Appendix~\ref{app:genai-log}); it is the authoritative record of the human/automated split for any stage of the project not already covered by the pipeline description in this chapter.

\section{Summary}
\label{sec:summary}
This chapter has set out an automated web UI testing pipeline and how a multimodal Vision-Language Model is evaluated under dynamic interaction scenarios. To our knowledge, this is among the first methodologies to apply a dual-path filtering architecture with automated fault injection to dynamic web UI anomaly detection. Beyond the pipeline's design, this chapter has given an explicit, code-grounded account of how the pipeline's ground-truth labels are structurally prevented from reaching the judge model (Section~\ref{sec:label_leak}), the two-stage pilot-then-power-analysed-formal-trial design behind the results reported next (Section~\ref{sec:exp_design}), and the division between automated execution, manually decided design, and AI-assisted implementation (Section~\ref{sec:division_of_labour}). The methodology changes how visual input is pre-processed and tests how far a modern VLM can act as an automated visual quality assurance tool; Chapter~\ref{chap:results_and_discussion} now reports what the formal 1{,}440-call trial found when it was applied.
